# Chapter 15: Physical Streaming Replication

![Chapter 15 physical streaming replication](diagram.svg)

## Concepts

- **Physical replication** copies a complete PostgreSQL cluster and replays its
  WAL. It is different from logical replication, which publishes selected row
  changes.
- **`pg_basebackup`** creates the initial physical copy. It must copy the
  primary into an empty data directory.
- **WAL** is the write-ahead log generated by the primary. The standby streams
  and replays WAL after the base backup is complete.
- **`standby.signal`** makes PostgreSQL start in recovery mode. The `-R` option
  to `pg_basebackup` creates it and writes `primary_conninfo`.
- The primary is writable. The standby is in recovery and is read-only for
  this lab.

## Goal

Manually initialize `postgres-replica` from `postgres-primary` with
`pg_basebackup`, start the copied cluster, and prove that WAL changes travel
from `db_a` to `db_b` across the lab router.

## Progression From Chapter 14

Chapter 14 finished the PostgreSQL process-model lessons. Chapter 13 already
created a writable primary at `10.10.21.20`, configured `wal_level=replica`,
created the `replicator` role, and routed database traffic through
`lab-router`.

The new question is not whether PostgreSQL can start. It is:

```text
How can a second PostgreSQL cluster get the primary's physical state
and continue receiving changes?
```

## What This Stage Adds

The cumulative Compose stack adds `postgres-replica`:

```text

writable                         starts as sleep infinity
      |                                  |

                 TCP 5432
```

The replica has the named volume `postgres_replica_data`, but chapter 15 does

```text
10.10.21.0/24 via 10.10.22.2
10.10.11.0/24 via 10.10.22.2
10.10.12.0/24 via 10.10.22.2
```

The sleeping command is deliberate. It gives us a safe shell in which to
prepare the replica volume before PostgreSQL starts.

## Tasks

### 1. Confirm the Starting State

**Predict:** What should be running in `postgres-replica` before a base backup?
Should PostgreSQL already have a cluster to serve?

**Run:**

```bash
bash scripts/compose-stage.sh 15 exec postgres-replica sh -c \
  'ip route; printf "\nReplica data directory:\n"; ls -la /var/lib/postgresql/data'
```

**Observe:** The route table includes the `db_a` route through `10.10.22.2`.
The data directory is empty on a fresh replica volume, and the container's
main command is still `sleep infinity`.

**Explain:** The replica needs a route to `10.10.21.20`, but it must not let the
normal PostgreSQL image initialization create an unrelated cluster first. A
physical standby starts from the primary's cluster, not from a new local
bootstrap.

### 2. Prepare an Empty Replica Directory

**Predict:** What will happen if `pg_basebackup` is pointed at a non-empty
directory? Why is clearing the directory dangerous if the command runs in the
wrong container?

**Run:** Enter the replica shell, then inspect the path before clearing it:

```bash
bash scripts/compose-stage.sh 15 exec postgres-replica sh
```

Inside that shell, run:

```bash
ls -la /var/lib/postgresql/data
rm -rf /var/lib/postgresql/data/*
install -d -o postgres -g postgres -m 700 /var/lib/postgresql/data
```

**Observe:** The directory is ready for PostgreSQL files and is owned by the
`postgres` user.

**Explain:** These commands operate on the mounted `postgres_replica_data`
volume because they are being run inside `postgres-replica`. Never run this
reset in `postgres-primary`; it would destroy the writable source cluster.
The reset is appropriate when intentionally repeating this manual chapter on
the disposable replica volume.

### 3. Take the Physical Base Backup

**Predict:** Which network address should receive the backup connection? Which
router interface is the next hop from the replica?

**Run:** Still inside the `postgres-replica` shell, run the original physical
copy command:

```bash
su postgres -c 'PGPASSWORD=replica_password pg_basebackup -h 10.10.21.20 -U replicator -D /var/lib/postgresql/data -Fp -Xs -P -R'
```

The important options are:

```text
-h 10.10.21.20  connect to the primary
-U replicator    use the replication role
-D ...           write into the empty replica data directory
-Fp              plain file layout
-Xs              stream WAL during the backup
-P               show progress
-R               create standby.signal and primary_conninfo
```

After it completes, inspect the two standby markers:

```bash
ls -l /var/lib/postgresql/data/PG_VERSION \
  /var/lib/postgresql/data/standby.signal
```

**Observe:** `pg_basebackup` reports progress and exits successfully. The
directory contains `PG_VERSION` and `standby.signal`.

**Explain:** The copied files are a physical cluster, not an SQL dump. The
`-R` option records enough connection information for PostgreSQL to reconnect
to the primary and enter recovery mode.

### 4. Provide Credentials for WAL Streaming and Start PostgreSQL

**Predict:** Is the `PGPASSWORD` used for `pg_basebackup` automatically saved
for later WAL connections? What happens if the standby has no password file?

**Run:** Still inside the replica shell, create the password file used by the
`postgres` user for subsequent replication connections:

```bash
printf '*:*:*:replicator:replica_password\n' > /var/lib/postgresql/.pgpass
chown postgres:postgres /var/lib/postgresql/.pgpass
chmod 600 /var/lib/postgresql/.pgpass
```

Now start the copied server in the foreground:

```bash
su postgres -c 'postgres -D /var/lib/postgresql/data'
```

Leave this command running. Open a second terminal for the remaining checks.

**Observe:** The first terminal shows PostgreSQL starting from the copied
data directory. It remains attached to the terminal because this is the
manual process model lesson.

**Explain:** `PGPASSWORD` is an environment variable for the one
`pg_basebackup` command. The `.pgpass` file is needed when the standby later
opens its own WAL connection. The password file is deliberately restricted to
mode `600`.

### 5. Verify Recovery and Streaming

**Predict:** What should `pg_is_in_recovery()` return on the primary and on
the replica? What state should the primary report for the replica client?

**Run:** In the second terminal:

```bash
bash scripts/compose-stage.sh 15 exec -T postgres-replica \
  psql -U labadmin -d labdb -c 'SELECT pg_is_in_recovery();'

bash scripts/compose-stage.sh 15 exec -T postgres-primary \
  psql -U labadmin -d labdb -c \
  'SELECT client_addr, state FROM pg_stat_replication;'

bash scripts/compose-stage.sh 15 exec -T postgres-primary \
  psql -U labadmin -d labdb -c 'SELECT pg_is_in_recovery();'
```

**Observe:** The replica returns `t`, the primary returns `f`, and the primary
reports a row similar to:

```text
 client_addr  |   state
--------------+-----------
 10.10.22.20  | streaming
```

The exact table formatting may vary.

**Explain:** `t` means the replica is in recovery and replaying the primary's
WAL. `streaming` means the primary has an active WAL sender connection to the
replica. The network path and PostgreSQL `pg_hba.conf` policy both had to work.

### 6. Prove WAL Replay and Read-Only Behavior

**Predict:** If the primary receives a new row, how will the replica get it?
Should an `INSERT` on the replica succeed?

**Run:** Insert on the primary, then read from the replica:

```bash
bash scripts/compose-stage.sh 15 exec -T postgres-primary \
  psql -U labadmin -d labdb -c \
  "INSERT INTO users (name) VALUES ('physical-replication-test');"

sleep 2

bash scripts/compose-stage.sh 15 exec -T postgres-replica \
  psql -U labadmin -d labdb -c \
  "SELECT name FROM users WHERE name = 'physical-replication-test';"
```

Now deliberately try a write on the standby:

```bash
bash scripts/compose-stage.sh 15 exec -T postgres-replica \
  psql -U labadmin -d labdb -c \
  "INSERT INTO users (name) VALUES ('should-fail-on-standby');"
```

**Observe:** The first query succeeds, the row appears on the replica after
WAL replay, and the last command fails with an error such as:

```text
ERROR:  cannot execute INSERT in a read-only transaction
```

**Explain:** The primary generates WAL for the insert. The standby receives
and replays that WAL, so the row becomes visible without a second application
write. Physical standby recovery prevents writes that would diverge the copied
cluster.

## Expected Observations

The complete manual flow is:

```text
postgres-primary 10.10.21.20
        |
        | TCP 5432, WAL stream
        v
lab-router 10.10.21.2 <-> 10.10.22.2
        |
        v
postgres-replica 10.10.22.20
        |
        +-- pg_is_in_recovery() = t
        +-- standby.signal exists
        +-- primary rows are replayed
        +-- local writes are rejected
```

The primary's `pg_stat_replication` row is stronger evidence than a successful
one-time TCP connection: it shows PostgreSQL is actively sending WAL.

## Break It: Use a Non-Empty Scratch Directory

This is one controlled failure. It deliberately targets `/tmp`, not the live
replica data directory, so it cannot damage the working standby.

**Predict:** What should `pg_basebackup` do when its destination already has a
file? Which layer reports the failure?

**Run:** In a new terminal, run:

```bash
bash scripts/compose-stage.sh 15 exec postgres-replica sh
```

Inside that shell, run:

```bash
rm -rf /tmp/replication-break
install -d -o postgres -g postgres -m 700 /tmp/replication-break
touch /tmp/replication-break/already-here
su postgres -c 'PGPASSWORD=replica_password pg_basebackup -h 10.10.21.20 -U replicator -D /tmp/replication-break -Fp -Xs -P -R'
```

**Observe:** `pg_basebackup` fails because the destination is not empty. This
is a client-side data-directory precondition, not a routing failure.

**Explain:** A physical base backup must not be merged into an unrelated
cluster. The safe recovery is to remove only the scratch directory, not the
real `PGDATA`:

```bash
rm -rf /tmp/replication-break
exit
bash scripts/compose-stage.sh 15 exec -T postgres-primary \
  psql -U labadmin -d labdb -c \
  'SELECT client_addr, state FROM pg_stat_replication;'
```

The existing standby should still report `streaming`.


This preserves the named volumes by default. Use `down -v` only when you
