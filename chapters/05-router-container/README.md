# Chapter 05: Multi-Homed Router Container

![Chapter 05 multi-homed router](diagram.svg)

## Key Concepts

### What Does Multi-Homed Mean?

A **multi-homed** system has more than one network interface connected to
different networks.

In this lab, the `lab-router` container is attached to all six Docker bridge
networks.

Conceptually:

```text
                    lab-router

          +-----------------------------+
          |                             |
public_a  | eth? 10.10.1.2/24           |
public_b  | eth? 10.10.2.2/24           |
app_a     | eth? 10.10.11.2/24          |
app_b     | eth? 10.10.12.2/24          |
db_a      | eth? 10.10.21.2/24          |
db_b      | eth? 10.10.22.2/24          |
          |                             |
          +-----------------------------+
```

The exact interface names may vary, but the router should have one interface
inside each lab subnet.

---

### Connected Routes

When Linux assigns an IP address and prefix to an interface, it automatically
creates a route for that directly connected subnet.

For example, if the router receives:

```text
10.10.11.2/24
```

on one interface, Linux automatically knows:

```text
10.10.11.0/24 is directly connected
```

The routing table may contain an entry similar to:

```text
10.10.11.0/24 dev eth2 scope link src 10.10.11.2
```

This is called a **connected route**.

We do not need to manually add a static route on the router for a network that
the router is already directly connected to.

---

### What Is Packet Forwarding?

A Linux host receives packets transmitted over a network at the kernel level,
processes them, and directs them to the correct application or socket.

A router's primary job is directing packets toward their destination.

Think of a router as a middleman that receives packets and decides which route
or interface should be used to move them closer to the destination.

On a network, an interface is the connection point through which the kernel
sends and receives network traffic.

In our case, the router container has multiple interfaces because it is attached
to multiple Docker networks.

A router must be able to receive a packet on one interface and send it out
through another interface.

That behavior is called **IP forwarding**.

IP forwarding is the ability of a Linux host or container to receive a packet
that is not destined for itself and forward that packet toward another host.

For example, we have two containers:

1. `app-a-test`
2. `app-b-test`

`app-a-test` is on `app_a` and `app-b-test` is on `app_b`.

For `app-a-test` to eventually reach `app-b-test`, we need a router connected to
both networks.

```text
app-a-test
10.10.11.10
     |
     | packet destined for 10.10.12.10
     v
lab-router
10.10.11.2
     |
     | forward packet
     v
lab-router
10.10.12.2
     |
     v
app-b-test
10.10.12.10
```

The router receives the packet on its `app_a` interface and forwards it out
through its `app_b` interface.

---

### Endpoint Traffic vs Forwarded Traffic

These are different:

```text
router itself sends or receives a packet
```

and:

```text
router receives a packet for another host and forwards it
```

For example:

```text
lab-router -> ping 10.10.12.10
```

is traffic generated by the router itself.

But:

```text
app-a-test -> lab-router -> app-b-test
```

is **forwarded traffic**.

This distinction becomes important later when we add firewall rules because
Linux handles locally generated traffic and forwarded traffic differently.

---

### IPv4 Forwarding

Linux controls IPv4 forwarding with a kernel setting:

```text
net.ipv4.ip_forward
```

To check the current status:

```bash
sysctl net.ipv4.ip_forward
```

Disabled:

```text
net.ipv4.ip_forward = 0
```

Enabled:

```text
net.ipv4.ip_forward = 1
```

For the `lab-router`, forwarding must be enabled.

## Router Configuration

IPv4 forwarding is configured in the Chapter 05 Docker Compose file.

The `lab-router` service contains:

```yaml
services:
  lab-router:
    build:
      context: chapters/05-router-container/router
    image: docker-networking-vpc-lab/lab-router:forwarding
    cap_add:
      - NET_ADMIN
      - NET_RAW
    sysctls:
      net.ipv4.ip_forward: "1"
    command: ["sleep", "infinity"]
```

The important section is:

```yaml
sysctls:
  net.ipv4.ip_forward: "1"
```

Docker applies this setting while creating the router container's network
namespace.

This means IPv4 forwarding is enabled before the main container process begins
running.

---

### Why We Do Not Set `ip_forward` Inside the Entrypoint

You might expect the router entrypoint to contain:

```sh
sysctl -w net.ipv4.ip_forward=1
```

However, in this container `/proc/sys` is mounted read-only.

Inside the router:

```bash
mount | grep /proc/sys
```

shows something similar to:

```text
proc on /proc/sys type proc (ro,nosuid,nodev,noexec,relatime)
proc on /proc/sysrq-trigger type proc (ro,nosuid,nodev,noexec,relatime)
```

The important option is:

```text
ro
```

which means read-only.

`sysctl -w` ultimately attempts to write to:

```text
/proc/sys/net/ipv4/ip_forward
```

so running:

```bash
sysctl -w net.ipv4.ip_forward=1
```

inside the container results in:

```text
sysctl: error setting key 'net.ipv4.ip_forward': Read-only file system
```

This is separate from Linux capabilities.

The router has:

```yaml
cap_add:
  - NET_ADMIN
  - NET_RAW
```

but capabilities do not make a read-only mount writable.

So:

```text
NET_ADMIN present
        +
/proc/sys mounted read-only
        =
sysctl write still fails
```

Docker Compose therefore sets the sysctl during container creation instead.

The router entrypoint only needs to run the main container command:

```sh
#!/bin/sh
set -eu

exec "$@"
```

## Test Router Endpoint Connectivity

Because the router is directly connected to every subnet, it should be able to
reach the diagnostic containers itself.

> Note: for this specific lab, the `lab-router` was attached to every network
> when the networks were created. The router is therefore directly connected to
> all six Layer-3 networks.

From inside `lab-router`, ping `app-a-test`:

```bash
ping -c 2 10.10.11.10
```

Then ping `app-b-test`:

```bash
ping -c 2 10.10.12.10
```

You should see something similar to:

```text
2 packets transmitted, 2 packets received, 0% packet loss
```

for both containers.

These tests prove that the router itself can communicate with hosts on its
directly connected networks.

This is **endpoint connectivity**.

The traffic is:

```text
lab-router
     |
     | packet generated by router
     v
app-a-test
```

or:

```text
lab-router
     |
     | packet generated by router
     v
app-b-test
```

This does not yet prove that one client can reach another client through the
router.

It only proves that the router itself can reach endpoints on its directly
connected networks.

## Important Observation

At this point, the router knows about all six networks:

```text
lab-router
     |
     +--> 10.10.1.0/24
     +--> 10.10.2.0/24
     +--> 10.10.11.0/24
     +--> 10.10.12.0/24
     +--> 10.10.21.0/24
     +--> 10.10.22.0/24
```

But the individual containers still only know about their own connected
networks.

For example, `app-a-test` may only have:

```text
10.10.11.0/24 dev eth0 scope link src 10.10.11.10
```

Suppose `app-a-test` wants to send a packet to:

```text
10.10.12.10
```

which belongs to:

```text
10.10.12.0/24
```

The packet must eventually be sent to the router:

```text
10.10.11.2
```

But `app-a-test` does not automatically know that `10.10.11.2` is the next hop
for reaching `10.10.12.0/24`.

It would need a route such as:

```text
10.10.12.0/24 via 10.10.11.2
```

The router existing does not automatically add that route to the client.

This is the key distinction:

```text
router exists
!=
clients automatically use router
```

In the next routing stage, we will teach the client containers where to send
traffic for remote networks.

## Break It

IPv4 forwarding is currently configured with:

```yaml
sysctls:
  net.ipv4.ip_forward: "1"
```

To observe the effect of disabling forwarding, temporarily change it to:

```yaml
sysctls:
  net.ipv4.ip_forward: "0"
```

Recreate the router:

```bash
bash scripts/compose-stage.sh 05 up -d --force-recreate lab-router
```

Enter the router:

```bash
bash scripts/compose-stage.sh 05 exec lab-router sh
```

Check the value:

```bash
sysctl net.ipv4.ip_forward
```

Expected:

```text
net.ipv4.ip_forward = 0
```

Now observe the distinction between router-generated traffic and forwarded
traffic.

```text
router's own traffic
may still work

forwarded traffic
will not work
```

For example, the router can still send:

```bash
ping -c 2 10.10.12.10
```

because that packet originates from the router itself.

The kernel is not forwarding a packet from another host.

Conceptually:

```text
lab-router
     |
     | locally generated packet
     v
app-b-test
```

But forwarded traffic would look like:

```text
app-a-test
     |
     v
lab-router
     |
     | forwarding required here
     v
app-b-test
```

When:

```text
net.ipv4.ip_forward = 0
```

the router cannot perform that forwarding step.

At this chapter, the client routing tables have not yet been configured, so the
full forwarded-client test will be completed in the next routing chapter.

The purpose of this experiment is to understand what the kernel forwarding
setting controls.

## Key Mental Model

```text
multi-homed
= one node connected to multiple networks
```

```text
connected route
= route automatically created because an interface is directly attached to
  that network
```

```text
IP forwarding
= kernel behavior that allows packets arriving for another host to be moved
  between interfaces
```

```text
endpoint traffic
= traffic generated by or destined for the router itself
```

```text
forwarded traffic
= traffic passing through the router on its way between other hosts
```

And most importantly:

```text
router knows every connected subnet
!=
clients know how to reach remote subnets
```

The router is now ready.

The next step is teaching the clients to use it.
