# Chapter 07: Packet Tracing

![Chapter 07 packet capture path](diagram.svg)

## Key Concepts

### A Packet Has a Path

In Chapter 06, `public-a-test` learned to send traffic for the remote
application subnet to `lab-router`:

```text
public-a-test 10.10.1.10
        |
        | next hop 10.10.1.2
        v
lab-router
        |
        | connected route to app_b
        v
app-b-test 10.10.12.10
```

The packet enters the router through its `public_a` interface. It leaves
through the router interface attached to `app_b`. These are the router's
**ingress** and **egress** points for the request.

The reply takes the reverse path:

```text
app-b-test -> lab-router on app_b -> lab-router on public_a -> public-a-test
```

### What Does `tcpdump` Show?

`tcpdump` observes packets seen by a network interface. In this chapter:

- `-i any` observes all interfaces in the `lab-router` network namespace;
- `-nn` leaves IP addresses and port numbers numeric, without DNS or service
  name lookups;
- `icmp` limits the capture to the ICMP packets generated by `ping`.

The capture proves that packets crossed an interface. It does not prove that
an application accepted a payload. A successful `ping` adds evidence that the
destination replied.

### Request and Reply Packets

An ICMP echo exchange contains at least these two packet types:

```text
type 8  = echo request
type 0  = echo reply
```

For this lab, the useful fields are the source address, destination address,
packet type, and interface where the line was captured. Interface numbering
can vary; the addresses identify the role of each side.

## Goal

Use `tcpdump` inside `lab-router` to prove where a packet enters and leaves the
router. By the end, you should be able to identify:

- the request entering from `public_a`;
- the request leaving toward `app_b`;
- the reply entering from `app_b`;
- the reply leaving toward `public_a`.

## Tasks

### Task 1: Start the Lab

**Predict.** The Chapter 07 Compose file is empty, so predict that the stage
will still have seven services and the Chapter 06 routes will still work.

**Run.** In either terminal, from the repository root:

```bash
bash scripts/compose-stage.sh 07 up -d --build
bash scripts/compose-stage.sh 07 ps
```

**Observe.** The `ps` output should include the six `*-test` services and
`lab-router`, all with a running status. The exact container names and
interface names are not important.

**Explain.** There is no new container because this chapter changes how we
observe the existing route, not how packets are routed.

### Task 2: Confirm the Route You Will Trace

**Predict.** Traffic from `public-a-test` to `10.10.12.10` should use the
router's `public_a` address, `10.10.1.2`, rather than Docker's bridge gateway,
`10.10.1.1`.

**Run.** In Terminal B:

```bash
bash scripts/compose-stage.sh 07 exec public-a-test \
  ip route get 10.10.12.10
bash scripts/compose-stage.sh 07 exec public-a-test \
  ping -c 2 10.10.12.10
```

**Observe.** The route lookup should contain a line similar to:

```text
10.10.12.10 via 10.10.1.2 dev eth0 src 10.10.1.10
```

The ping should report two replies and `0% packet loss`. Extra fields such as
`uid 0` may appear.

**Explain.** This tells you what to look for in the capture: the request starts
at `10.10.1.10`, targets `10.10.12.10`, and first reaches `lab-router` at
`10.10.1.2`.

### Task 3: Capture the Forward Path and Return Path

**Predict.** One ping request should be visible entering `lab-router` from
`public_a` and leaving it toward `app_b`. The echo reply should appear in the
opposite direction.

**Run.** In Terminal A, start the capture first:

```bash
bash scripts/compose-stage.sh 07 exec lab-router \
  tcpdump -i any -nn icmp
```

Leave it running. In Terminal B, generate exactly one two-packet exchange:

```bash
bash scripts/compose-stage.sh 07 exec public-a-test \
  ping -c 2 10.10.12.10
```

When the replies are visible in Terminal A, press `Ctrl-C` there.

**Observe.** The exact interface names, packet IDs, and timestamps vary. Look
for these address and type combinations:

```text
10.10.1.10 > 10.10.12.10: ICMP echo request
10.10.12.10 > 10.10.1.10: ICMP echo reply
```

With `-i any`, the request is seen on the router's `public_a` side and on its
`app_b` side. The reply is seen on the `app_b` side and then the `public_a`
side. A capture may include more lines than this if other lab traffic is
running.

**Explain.** Label the four observations as follows:

```text
request on public_a  = ingress to lab-router
request on app_b     = egress from lab-router
reply on app_b       = ingress to lab-router
reply on public_a    = egress from lab-router
```

The source and destination IP addresses do not change in this chapter. The
router forwards the packet; it does not perform NAT.

### Task 4: Correlate Capture Evidence With the Route

**Predict.** The capture should agree with both route lookups: the source's
next hop is `10.10.1.2`, and the router's connected route sends the packet out
the interface carrying `10.10.12.2`.

**Run.** Inspect the router's addresses and route decision:

```bash
bash scripts/compose-stage.sh 07 exec lab-router ip addr
bash scripts/compose-stage.sh 07 exec lab-router ip route get 10.10.12.10
```

**Observe.** Find addresses for `10.10.1.2/24` and `10.10.12.2/24`. The route
lookup should select the interface whose source address is `10.10.12.2`.

**Explain.** `ip route get` shows the kernel's decision; `tcpdump` shows the
packets that followed that decision. The two tools answer different questions:

```text
ip route get = where Linux plans to send the packet
tcpdump      = where the packet was actually observed
```

### Task 5: Inspect a Single Router Interface

**Predict.** A capture on only the `public_a` interface will show the request
arriving and the reply leaving, but it will not show the router's `app_b` side.

**Run.** First find the interface carrying `10.10.1.2`:

```bash
bash scripts/compose-stage.sh 07 exec lab-router ip -o -4 addr show
```

Note the interface name on the line containing `10.10.1.2/24`. In Terminal A,
replace `INTERFACE_NAME` with that name:

```bash
bash scripts/compose-stage.sh 07 exec lab-router \
  tcpdump -i INTERFACE_NAME -nn icmp
```

In Terminal B, run the ping again:

```bash
bash scripts/compose-stage.sh 07 exec public-a-test \
  ping -c 2 10.10.12.10
```

Stop the capture with `Ctrl-C`.

**Observe.** You should see packets involving `10.10.1.10` and
`10.10.12.10` on the `public_a` side, but no capture lines from the `app_b`
interface. If the interface is wrong, the capture may be empty.

**Explain.** Selecting one interface is an observation filter. It does not
change routing or block packets. The packet can leave the router on another
interface even though this capture cannot see that interface.

## Expected Observations

At the end of the main experiment, you should have this evidence:

```text
source:      public-a-test 10.10.1.10
destination: app-b-test    10.10.12.10
request:     enters public_a, leaves app_b
reply:       enters app_b, leaves public_a
addresses:   unchanged; no NAT in Chapter 07
```

If the ping succeeds but the capture is empty, check that `tcpdump` is running
inside `lab-router`, that it uses `-i any`, and that Terminal B generated the
traffic after Terminal A started. If only the request appears, inspect the
destination route and return route before assuming a firewall problem.

## Break It: Hide Half the Path

This is a controlled observation failure. It does not change a route or a
container configuration.

1. Capture on the `public_a` interface as in Task 5.
2. Run the two-packet ping from `public-a-test`.
3. Explain why the `app_b` ingress and egress events are absent.

**Recovery.** Stop the single-interface capture with `Ctrl-C`, restart the
all-interface capture, and run the ping once more:

```bash
bash scripts/compose-stage.sh 07 exec lab-router \
  tcpdump -i any -nn icmp

# In another terminal:
bash scripts/compose-stage.sh 07 exec public-a-test \
  ping -c 2 10.10.12.10
```

Stop `tcpdump` after the replies appear. No Compose repair is needed because
the exercise changed only the observation point.
